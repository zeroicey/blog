前面几篇文章都是「在一台正经 x86 服务器上折腾服务」，这篇换个口味：**给一块巴掌大的香橙派装 OpenWrt，把它变成家里网络的「旁路由」**。

想在几十块钱的 ARM 板子上跑 OpenWrt，其实有不少现成方案。但这一路走下来，我结结实实踩了三个坑，最后还差点被一盏红灯骗得以为板子挂了。整个经历挺有代表性，所以写下来给后来人避坑。

> ⚠️ **替换说明**：文中主机名、局域网 IP、认证地址等均为虚构示例，照着做时请换成你自己的真实值。

## 为什么是香橙派 Zero 3

选这块板子的理由很朴素：便宜、省电、有千兆网口，而且**功耗低到可以 7×24 开着不心疼**。它的配置如下：

| 项 | 参数 |
| --- | --- |
| SoC | 全志 H618（4×Cortex-A53） |
| 内存 | 2GB |
| 网口 | 千兆（1×） |
| 存储 | TF 卡 + 16MB SPI Flash |
| 无线 | 板载（但主流内核没有好驱动，本文不依赖它） |

旁路由（side router）的定位也正好适合它：**不替换主路由，只是挂在局域网里，替一部分设备做透明代理、DNS 过滤这些「网络边沿」的活**。主路由继续负责拨号和无线，各司其职。

## 坑一：官方 OpenWrt 能启动，却装不了任何软件

开工第一步是选镜像。最"正统"的做法当然是去官方固件选择器，选 `xunlong_orangepi-zero3`，下一个 snapshot 镜像烧进 TF 卡。

烧录很顺利，板子也正常引导，SSH 进去，正当我准备装个软件时，`opkg update` 直接翻了车——**一个软件源都更新不了**。

后来才搞明白原因：OpenWrt 的 **snapshot（快照）镜像的软件源是"滚动"的**。也就是说，你烧的是某一天的快照，而这一天对应的软件源在服务器上只保留很短一段时间，之后就被下架了。等你真正开机去 `opkg update` 时，那一天已经"过期"，自然一个包都拉不到。

这是个很反直觉的坑：**镜像本身没坏，装包的功能却形同虚设**。对日常刷机党来说，snapshot 的"没软件源"足以劝退。

## 坑二：immortalWrt 一上电就 panic

既然官方快照不行，那就换个衍生发行版。immortalWrt 是社区很流行的一个 OpenWrt 分支，官方也提供了 zero3 的镜像。烧录、上电，结果**只有红灯，绿灯不亮**——按经验，这是典型的"内核没起来"。

排查了一圈才定位到根因：当时 immortalWrt 25.x 用的内核是 **6.6**，而全志 H616/H618 这个 sunxi 平台上，6.6 内核在加载 `ntfs3` 模块时会触发一个 **`sun6i_spi` 中断处理里的内核 panic**。这是一个社区里已经有人报过的已知 issue（搜 `immortalwrt#1680` 能看到原始 oops），现象就是：上电 → 只有红灯 → 彻底起不来。

绕开它的办法倒也简单：换 6.1 LTS 内核的镜像，或者干脆换一条内核已升级的分支。但当时这给我提了个醒——**在 sunxi 板子上选镜像，内核版本比发行版名字更重要**。

## 转折：一个「云编译」的仓库

卡在这两个坑里的时候，我找到了一个非常省心的路子：**GitHub 上的"云编译"仓库**。

这类仓库（我用的这个叫 [jym66/openWRT-OrangePiZero3](https://github.com/jym66/openWRT-OrangePiZero3)）本身不含系统源码，而是用 **GitHub Actions 定时自动从上游源码编译**，每周把编译好的固件发到 Releases 里。作者同时维护了两条线：

- **Lean lede 线**：基于 coolsnowwolf/lede（国内很流行的「大雕」分支），内核跟随上游更新；
- **immortalWrt 线**：基于 immortalwrt 官方分支。

对当时的我来说，最有价值的点有两个：一是**它的 lede 线已经在用 6.12 内核**，直接绕开了前面的 6.6 panic；二是**它识别 zero3 板型分毫不差**，`sunxi/cortexa53 → xunlong_orangepi-zero3`，不用自己改任何 target。

于是下载 lede 线的 `squashfs-sdcard.img.gz`，校验 sha256 → `dd` 烧卡 → 读回比对（这是上次烧坏 boot 分区换来的教训）。上电，绿灯……嗯，先别急，看下一个坑。

## 坑三：一盏红灯的虚惊

插电之后，我盯着板子，心里咯噔一下：**又只有红灯，绿灯不亮。**

难道又 panic 了？我差点就拔电重刷了。好在多留了个心眼，先拿 `arping` 探了一下默认地址 `192.168.1.1`——**居然有响应**。再 SSH 进去一看，系统好好的，内核 6.12.104，内存识别完整。

真相是：**Lean lede 这个分支根本没给这块板配绿色状态灯**。红灯只是电源灯，永远亮着；绿灯因为没被配置成「状态灯」而常灭。所以"只有红灯"在这种固件上是**正常的**，不能像官方镜像那样用"绿灯亮=引导成功"来判断。

> 这条经验很反直觉，值得单独划重点：**判断一块全志板子到底起来没有，别只看灯，用 `arping` / `ssh` 实测一下再说。**

## 真正装好之后，我都配了什么

确认系统正常后，就是把它调教成一台合格的旁路由。下面是几个关键步骤的要点（命令都精简过了，只保留核心）：

### 1. 静态 IP，并先关掉它自带的 DHCP

新固件默认是 `192.168.1.1`，而且默认开着 DHCP 服务器。如果直接插进现有局域网，它会**跟你主路由抢着发 IP**，造成"野 DHCP"。所以第一件事就是改静态 IP、关掉它的 DHCP：

```sh
uci set network.lan.ipaddr='192.168.0.10'      # 改到你的网段
uci set network.lan.gateway='192.168.0.1'
uci set network.lan.dns='192.168.0.1'
uci set dhcp.lan.ignore='1'                     # 先关掉 DHCP 抢发
uci commit network && uci commit dhcp
```

### 2. 透明代理（Fake-IP）

这固件预装了 OpenClash / PassWall 这类代理插件。旁路由场景下，选 **Fake-IP（增强）模式**最省心：客户端把网关/DNS 指向板子，境外域名解析成 `198.18.x.x` 的假 IP，再由代理内核按域名规则分流，国内直连、境外走代理，全程透明，客户端零配置。

### 3. 全屋接管 DHCP（可选但很爽）

如果想让**所有设备自动走旁路由**，可以让板子接管 DHCP：主路由关掉 DHCP，板子上重新开启，同时把下发的网关和 DNS 都指向板子自己。这样全屋设备一重连，就自动把流量交给旁路由了。

> ⚠️ 代价要想清楚：接管 DHCP 之后，**板子一旦断电，全屋就断网**。所以电源一定要弄牢。

这里还有个隐蔽坑：OpenWrt 的 dnsmasq 在启动时会做一次「局域网里是否已有 DHCP 服务器」的检测，检测到主路由还在发 DHCP 就直接拒绝服务。等主路由关了 DHCP、板子重启后它才会接管；想跳过这个检测，给 `dhcp.lan` 加 `option force '1'`。

### 4. AdGuard Home 去广告

`opkg install adguardhome` 就能装。它是**DNS 级别的去广告**：维护一份广告域名黑名单，广告域名直接解析到 `0.0.0.0`，页面里的第三方横幅、弹窗自然就加载不出来了。

装它唯一的讲究是跟代理的 DNS 串起来：让 AdGuard 监听 53，把上游指到 OpenClash 的 fake-ip DNS，这样广告被拦、境外域名照样走 fake-ip，互不干扰。最后全屋设备的 DNS 都指向板子即可。

> 提醒一句预期管理：DNS 去广告拦得了第三方广告横幅/追踪器，但**拦不了视频站内嵌的广告**（比如 YouTube 片头），那些得靠浏览器插件。

### 5. 校园网认证搬到板子上

我们网络有个需求：校园网要定期网页认证，断线了会自动掉。之前一直靠某台机器上跑一个 keep-alive 脚本认证，后来干脆把它也塞进板子——**正好它是 7×24 常开的那一台**。

这个 keep-alive 本身很简单：一个 Go 写的小程序，定期检测能不能上网，发现被重定向到认证页就 POST 账号密码登录。因为板子是 arm64 + musl，而原来的二进制是 x86 的，直接 `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build` 交叉编译一个静态版，丢到板子上配个每分钟的 cron 就完事。这一段我觉得挺能体现 ARM 板子的好处：**编译一次、常开跑着、不占主力机器的资源**。

### 6. 监控

最后给板子装上监控 agent（我用的是 [Komari](https://github.com/komari-monitor/komari)，一个 Go 写的轻量监控），这样在面板上就能看到它的 CPU / 内存 / 磁盘 / 网络曲线。这里同样交叉编译了一份 arm64 二进制，并写了个 procd 后台服务让它开机自启。

## 收尾：几条血泪经验

折腾这一圈，最值钱的其实是这几条，单独列出来：

1. **刷全志板，内核版本比发行版名字重要。** 6.6 有 `ntfs3`+`sun6i_spi` 的 panic，6.1 / 6.12 就没事。
2. **官方 snapshot 的"没软件源"是设计使然，不是你的问题。** 日常自用优先选带有长期软件源的 release 或第三方云编译仓库。
3. **别只靠灯判断板子死活。** lede 系固件可能不点绿灯，只剩红灯也可能早就起来了，实测 `arping`/`ssh`。
4. **软重启可能挂死。** 全志板子上 `reboot` 偶尔起不来，需要物理断电冷启动，改配置优先用局部 reload。
5. **旁路由接管 DHCP 前，想清楚单点故障**，电源务必弄牢。

## 结语

从「官方镜像没软件源」到「红灯虚惊」，这块小板子最终被我调教成了一台稳定的网络边沿盒子：透明代理、去广告、校园网认证、全屋 DHCP、监控，全在一台功耗个位数的设备上常开运行。主力服务器继续干算力和存储的活，各司其职。

如果你也手边有块闲置的板子，不妨照着这条路试一次——**便宜的板子真能顶一台正经路由器用**，关键是要选对镜像、选对内核。
