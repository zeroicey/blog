如果你让 AI 助手维护一个项目超过一周，一定会遇到这个问题：**每次开新会话，它都失忆了**。

上周定下的架构决策，它不知道；前天踩过的部署坑，它会再踩一遍；服务器上哪个目录是不能碰的，得靠你每次口头提醒。上下文窗口再大也解决不了——会话结束，一切归零。

我在三个真实项目（一个多应用工作台、一个个人日记服务、一个人员登记系统）里用了一套自己攒的「项目记忆」方案。它不玄乎：本质就是 **markdown 文件 + 一个 200 行的 pi 扩展**。运行了一段时间后，它已经实际参与了几十次生产部署、一次惊险的服务器配置抢救，也暴露出了自己的问题。

这篇文章记录它的现状——包括好用的部分和已经露馅的部分。**这是一篇活文档**：方案还在迭代，我会随更新修订本文，你看到的永远是当前状态。

# 方案全貌：三层记忆模型

先看整体设计。核心思路是模仿缓存的分层结构，把「记忆」按访问频率和成本分成三层：

| 层 | 载体 | 性质 | 进入上下文的方式 |
| --- | --- | --- | --- |
| L1 永久准则 | `.pi/APPEND_SYSTEM.md` | 铁律、不变量、已知陷阱清单 | 静态注入，每会话必载 |
| L2 近期记忆 | `.ai/` 的摘要 | 最近发生了什么 | 扩展每轮动态注入 ≤1.8KB |
| L3 全量检索 | `.ai/` 全文 + 事件库 | 细节与历史 | 模型按需 `read` / `ctx_search` |

对应到磁盘上是两个目录：

```
project/
├── .pi/                      # agent 配置
│   ├── APPEND_SYSTEM.md      # L1：永久准则（含已知陷阱区）
│   ├── extensions/
│   │   └── memory.ts         # L2：自动注入扩展
│   └── skills/
│       └── remember-*/       # 写路径的记忆 skill
└── .ai/                      # 项目记忆本体
    ├── README.md             # 目录职责 + 规则 + 索引
    ├── worklog/              # 每日流水账（权威历史）
    ├── decisions/            # ADR 决策记录
    ├── requirements/         # 需求文档（带状态行）
    ├── architecture/         # 当前有效的架构文档
    ├── runbooks/             # 标准流程手册（唯一事实源）
    ├── archive/              # 死文档
    └── inbox/                # 待消化片段中转站
```

# 读路径：一个扩展解决自动注入

L2 是整套方案的发动机。`.pi/extensions/memory.ts` 挂在 pi 的 `before_agent_start` 事件上，**每一轮对话开始前**，把近期记忆摘要追加进系统提示：

```typescript
// 简化后的核心逻辑
pi.on("before_agent_start", (event) => {
  const digest = buildDigest(root); // ≤1.8KB
  return { systemPrompt: `${event.systemPrompt}\n\n${digest}` };
});
```

摘要包含三样东西：

- **最近 4 个 worklog 文件的主题**（只取标题，不取正文）
- **最新 5 条决策的标题**
- **inbox 里未消化的片段列表**

两个关键的设计决定：

**第一，注入克制。** 上限 1.8KB，只给标题级钩子。模型看到「2026-08-23 管理端剩余分组全量重构 + 磁盘满与 .env 抢救事故」这个标题，如果判断和当前任务相关，自己去 read 原文。全文灌入的话，几百 KB 的历史很快就会把上下文撑爆。

**第二，mtime 指纹缓存。** 会话进行中新写了记忆，下一轮摘要自动刷新——靠对比文件 mtime 列表，变了才重算。这意味着「刚发生的写入立刻可见」，收尾写的 worklog 在同一个会话内就能被后续轮次感知。

效果是：新会话的第一轮开始，模型就已经知道「最近在忙什么、最近定了什么」。不再需要你复述背景。

# 写路径：skill + 收尾纪律

读是自动的，写目前主要靠约定。我建了四个 remember-* skill：

| skill | 职责 |
| --- | --- |
| `remember-worklog` | 会话实质工作 → 当日 worklog |
| `remember-decision` | Why 层面的选择（含否决项）→ ADR |
| `remember-runbook` | 可复现流程 → runbook，worklog 留指针 |
| `remember-requirement` | 需求状态变化 → 同步状态总表 |

配套几条蒸馏规则：

- **先查重再写**：同主题已存在 → 更新不新建
- **坑用 ⚠️ 标记；踩两次升级**：同一坑第二次出现，提炼进 APPEND_SYSTEM 的「已知陷阱」区——那里是静态注入的 L1，以后每个会话必看
- **流程只在 runbook**：worklog 发现可复现流程就沉淀成 runbook，原文只留一行指针

另外还有一层兜底：context-mode 扩展自动捕获事件级记忆（决策、报错、阻塞），用 `ctx_search` 全文检索。分工是——**事件库是廉价原材料，`.ai/` 是人工沉淀的权威版本**。

这套东西实际运转起来的样子，举两个真例：

**例一**：一次生产部署事故里，清理旧 release 时把所有 release 都软链着的 `.env` 连带删掉了，线上服务一旦重启就丢配置。抢救过程（从 `/proc/<pid>/environ` 导出运行中进程的环境变量）完整写进了当日 worklog，核心经验提炼成一条：「/proc/<pid>/environ 是抢救运行中服务配置的最后手段」。下次再遇到类似事故，模型检索一下就有现成方案。

**例二**：一个存储架构决策（删除操作改走 Worker 网关签名）的 ADR 里，不仅记录了采纳方案，还记录了两个被否决的方案及否决理由。两周后另一个模块遇到相似问题，模型直接引用了这份 ADR 的结论，没有重新踩坑。

# 实战检验：它在真实项目里的表现

三个项目的使用强度不同，正好形成一组对照：

| 项目 | 形态 | 记忆规模 | 特点 |
| --- | --- | --- | --- |
| koma | 多应用工作台 + 双服务器运维 | 68 个 worklog / 604K | 一天多个 worklog，强度最高 |
| serenique | 全栈日记服务（四端） | 95 个 worklog / 1.5M | 记忆纳入 git，约 35% 的提交是记忆维护 |
| registry | Bun + React 登记系统 | 5 个 worklog / 96K | 精简版：决策单文件化，无 archive |

serenique 的那个 35% 值得单独说：三周里 498 个提交有 176 个动过 `.ai/`。这个比例说明记忆维护不是装饰性动作——它已经是工作流的一部分。代价后面会讲。

# 已暴露的问题：诚实清单

跑了这几周，下面这些问题是真金白银踩出来的。这部分可能是全文最有价值的部分。

## 问题 1：写路径靠自觉，这是最大的洞

读路径自动化了，写路径却只有 skill 描述和一句「收尾动作」约定。后果：

- 模型某轮忘了收尾，或者判断「这次改动不算实质产出」→ 记忆静默丢失
- 你无法区分「没发生值得记的事」和「忘了记」
- 写入内容没有校验机制，长期存在幻觉沉淀风险

实证就在眼前：koma 的 inbox 里躺着一条 8 月 16 日的片段，「消化后清空」的约定一周没有兑现。

## 问题 2：「踩两次才升级」存在循环依赖

坑升级到 L1 的前提是识别出「这是第二次」。但识别第二次需要记住第一次，而第一次埋在某个不会被注入的 worklog 文件深处——也就是说，**这条蒸馏管线的入口恰恰建立在系统最不可靠的环节上**。很多坑可能永远停在 worklog 里，等不到第二次。

## 问题 3：注入的是标题，不是教训

对改变行为最有价值的是「⚠️ 坑 + 绕法」这种具体指令，但 L2 只注入标题。标题只能起路标作用，要求模型主动深读——而模型对一个看起来不相关的历史标题，深读动力不足。另外注入按时间倒序取最新的，一个月前的关键决策会彻底滑出窗口，哪怕它和当前任务高度相关。

## 问题 4：同一事实存五处，一致性靠人肉

一个坑可能同时出现在 worklog 正文、README 索引、ADR、APPEND_SYSTEM 陷阱区、runbook 五个地方。「更新不新建」这类规则全是纪律约束，没有机制保障。最明显的症状是 **koma 的 README 已经膨胀到 20KB**——里面的「最近工作」链条实际上是 worklog 的二次摘要，和 worklog 本体大量重复，等于偷偷长出了一个无上限、无过期机制的第四层。

## 问题 5：三份手工 fork 正在分叉

memory.ts 在三个项目里各有一份，已经开始各自演化（koma 版支持一天多文件、registry 版按 mtime 排序）。bug 修复不会互相传播，半年后就是三套难以合并的方言。

## 问题 6：持久性策略混乱

koma 根目录不是 git 仓库——604K 运营记忆零版本控制躺在单块磁盘上；registry 把 `.ai` 加了 gitignore——无备份无历史；只有 serenique 纳入了 git。**一个记忆系统，自身的耐久性反而是最随意的**，这说不过去。

# 已启动的修复：写路径守卫

针对问题 1，第一个机制化的修复已经在 koma 上线（就是今天）。思路是把「该写的时刻」变成机制：

```
tool_call 钩子                agent_settled                 强制收尾轮
┌─────────────────┐    ┌──────────────────────┐    ┌──────────────────────────┐
│ 跟踪 edit/write  │ →  │ ≥3 次代码编辑？        │ →  │ sendMessage(triggerTurn) │
│ 碰过 .ai/ 即视为 │    │ 当日 worklog 更新过？  │    │ 注入提醒，模型必须显式    │
│ 已收尾           │    │ 都没有 → 该提醒了      │    │ 处理：写 or 说明为何不写  │
└─────────────────┘    └──────────────────────┘    └──────────────────────────┘
```

几个关键取舍：

- **选 `agent_settled` 而非会话退出钩子**：退出时进程都要没了，触发不了响应，只能退化成下个会话补课
- **强制触发一轮，而不只是 UI 通知**：免费的通知模型看不到也行动不了。强制一轮意味着「写与不写」成为模型的显式判断，哪怕回答「本次无可记内容」——那也是判断，不是静默丢失
- **不自动代写内容**：守卫只保证动作被评估，内容仍由模型按模板产出。自动代写会产生幻觉沉淀，比不写更糟
- 三道防打扰闸：每会话最多提醒一次 / 编辑数阈值 / `/memory-guard-skip` 手动关闭

这个守卫刚上线，还没经过实战校准（阈值是否合适、误报率多少都待观察）。**观察 3~5 个真实会话后**，再决定是否移植到另两个项目。

# 后续路线图

按优先级排，也是本文未来更新的方向：

1. **worklog compaction** —— 95 个文件线性增长，一年后检索质量必然劣化。计划做定期蒸馏任务：旧 worklog 压缩成「已验证经验」页，原文归档
2. **README 索引自动生成** —— 由扩展从文件名 + 标题生成索引，消灭问题 4 里的人肉三重记账
3. **守卫移植与 fork 收敛** —— memory-guard 验证有效后，三份 memory.ts 一并收敛成一个共享参数化扩展
4. **统一持久化策略** —— `.ai/` 全部纳入 git（敏感项除外），koma 补定时备份
5. **inbox 与 requirements 减法** —— inbox 已基本被 context-mode 替代，考虑摘除；requirements 层对单人项目偏重，评估并入 ADR 头部

# 总结：现阶段值得抄的是什么

如果只带走三句话：

1. **分层是对的**：铁律静态注入、近期记忆摘要注入、全量按需检索——克制注入是整套方案的基石，别上来就把记忆全文塞上下文
2. **读路径可以完全自动化，200 行扩展就够**；写路径的机制化才是难点，也是当前的主攻方向
3. **记忆系统自身也要当作软件来维护**：它会有 bug、会熵增、需要 compaction——把它当成项目的一部分，而不是一个装了就完事的插件

至于那些还没修的问题——README 膨胀、fork 分叉、「踩两次」的循环依赖——它们就明晃晃地写在上面，作为这套系统当前状态的如实快照。等修复落地，本文相应小节会被改写而不是删除：一篇讲「项目记忆」的博客，理应用项目记忆的方式来更新自己。
